## 🌌 Fuel & Custom-Map Bugfix Pass (triaged 2026-07-19, late) — new top priority

Six fresh notes landed at the top of this inbox; all checked against the current repo (`games/black-hole-in-one`) before triaging below. This arc jumps ahead of Map Maker's remaining P3 tail and the paused rest of Golf Mode Catch-Up (see the reprioritization note up top) — confirmed bugs and a clean root-caused HUD fix beat flourish, same call as GOLF-1/2 earlier today.

- [x] **P0 · FUEL-4 — Bug — restarting a custom/shared map discards it and generates a random golf hole instead.** ✅ **Shipped 2026-07-20** (`f7d473c`) — root cause: `main.js`'s `startRun()` wrapper routed `S.mode === 'custom'` to `game.startRun(mode)` (golf's `genHole()`) instead of `game.startCustomMap()`, and the loaded `mapData` was never retained anywhere to reload even if it had. Fix: `startCustomMap()` retains `mapData` on `world.activeMapData` (pickups cloned, not the same array, since in-play collection splices `world.pickups` and would otherwise permanently deplete the retained source); restart now reloads via `game.startCustomMap(world.activeMapData)`, falling back to Endless only if nothing's retained (fresh page load resuming a stale `'custom'` last-mode). Full trail: [Dev Log](../../archive/dev-logs/black-hole-in-one.md).
- [x] **P0 · FUEL-5 — Bug — thruster mode's fuel bar doesn't visually drain while thrusting.** Shipped 2026-07-20 (0a23e79). Root cause: explore.js's step(dt) called burnFuel() every physics frame under thrust but never called hooks.bar() in that block, so the HUD only refreshed on unrelated discrete events (pickups, landing, upgrades). Fix: added the missing hooks.bar() call right after burnFuel(...), matching the pattern already used at every other fuel-spend call site. Regression test added (tests/black-hole-in-one.test.mjs, FUEL-5), verified to fail without the fix and pass with it. Also verified live against the deployed page: drove the running game's own explore.js/state.js module instances directly, and #exploreFuelBar's rendered width visibly ticked 100% to 96% over 30 held-thrust frames.
- [x] **P1 · FUEL-6 — Bug — fuel never drains in Custom Map mode.** ✅ **Shipped 2026-07-20** (`8bca4cf`) — root cause: `gameplay.js`'s `launch()` gated both the fuel spend (`S.fuel -= 15`) and the zero-fuel launch guard (`if (S.fuel <= 0) return false`) to `S.mode === 'endless'` only — `'custom'` fell through both untouched, so a custom map could be flown forever on any fuel value. Fix: widened both guards to `S.mode === 'endless' || S.mode === 'custom'`, and folded the zero-fuel check into the same branch as the weak-drag cancel (FUEL-3's phase-restore pattern) so a failed 0-fuel aim restores `S.phase` instead of stranding it at `'aiming'` — this fix is mode-agnostic, so it resolves **GOLF-4** below too, not just the Custom Map case. Shipped in the same commit as FUEL-7/FUEL-8 (same code area). Regression: 2 new unit tests in `tests/black-hole-in-one.test.mjs` (confirmed failing pre-fix via `git stash`) + a live-DOM e2e case in `scripts/e2e.mjs`. Full suite 408/408, e2e 15/15. Verified live: fetched the deployed `gameplay.js` from `yevrap.github.io` and confirmed the widened guard is served. Full trail: [Dev Log](../../archive/dev-logs/black-hole-in-one.md).
- [x] **P1 · FUEL-7 — Bug — Custom Map's fuel bar never visually updates.** ✅ **Shipped 2026-07-20** (`8bca4cf`) — root cause: `ui.js`'s `updateBar()` only called `setFuelBar('endlessFuelBar', S.fuel)` inside its `if (S.mode === 'endless')` branch — but `startCustomMap()` unhides the same `#bar`/`#endlessFuelBar` element for custom play too, so the bar was visible and just never told to move. Fix: widened that branch's fuel-bar call to also cover `'custom'`; the stardust text line stays endless-only, unchanged (hole/par/strokes/badge logic below already ran for both modes). Regression: live-DOM e2e case in `scripts/e2e.mjs` asserting `#endlessFuelBar`'s rendered `style.width` tracks `S.fuel` in custom mode. Verified live in the browser: reproduced the exact sequence (leftover golf fuel → enter custom map → flick) and screenshotted the bar visibly ticking from 100% to 85%.
- [x] **P1 · FUEL-8 — Bug — fuel doesn't reset entering or restarting a custom map; leftover golf fuel carries over.** ✅ **Shipped 2026-07-20** (`8bca4cf`) — root cause: `startCustomMap()` reset strokes/hole/orbit/trail/etc. but never touched `S.fuel`, unlike golf's `startRun('endless')` which explicitly sets `S.fuel = 100`. Every entry into custom play — first load from My Maps, a shared `?map=` link, and `restartBtn`/`main.js`'s `startRun('custom')` wrapper — funnels through `startCustomMap()`, so whatever `S.fuel` golf (or a prior custom session) left behind just carried forward, and restarting the same custom map didn't top it back up either. This was the literal bug behind "when I use fuel in golf mode, it does not reset in a custom map." Fix: `startCustomMap()` now sets `S.fuel = 100` on entry, mirroring golf's line exactly. Regression: unit test in `tests/black-hole-in-one.test.mjs` covering both fresh entry and restart-via-`activeMapData` (confirmed failing pre-fix).
