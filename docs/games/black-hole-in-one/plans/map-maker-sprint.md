## Goal

Three asks, in Yev's own words:
1. **Use the minimap as the map maker**, with fine adjustments made once it's closed.
2. **Maps must be playable and shareable.**
3. **A glossary of map items and how they work.**

(2) is mostly already shipped — Map Maker has had Test Play since MM-1 and URL share/import since MM-3, and a shared `?map=` link already drops a visitor straight into "Play this map" without touching the editor. The real gap in (2) is that **locally saved** maps (the My Maps drawer) can only be *loaded into the editor*, not played directly — that's MM-11 below. (1) and (3) are net-new design.

## Why the minimap needs to exist at all

Editor mode today shows the **entire course at once**, scaled to fit the screen — there's no camera, so "drag the planet" has always been the only way to reposition anything, and it's worked fine because the whole map was always on-screen already. That stops being true the moment maps can be **bigger than one screen** (Explore's chunked world is 200×200 and uses camera-follow; a golf-scale course is small and fits fine). **MM-6 (map size chooser) is the reason MM-16 becomes necessary** — once a builder can choose a large canvas, they need some way to see and place bodies across the whole thing without panning by dragging a planet to the edge of the visible area over and over.

## Design: the minimap-as-editor

**Two modes of the same editor, not two separate screens:**

- **Overview (minimap) mode** — a zoomed-out view of the *entire* course canvas, reusing the Explore star map's visual language (`renderStarMap()` in `ui.js`: dark background, a fitted grid, glowing markers for the tee/black hole/planets/pulsars instead of chunk-discovery dots). Opened via a new "🗺️ Overview" button in the `#editorBar`, alongside the existing Test Play control.
  - **Coarse placement here.** Tap-drag a body to reposition it anywhere on the full canvas in one motion — no panning needed, because the whole map is visible at overview scale. Add Planet / Add Pulsar (existing `addPlanet()`/`addPulsar()`) drop the new body at a sensible default spot in overview coordinates, same as today.
  - Bodies render as simplified glyphs (dot + color) at overview scale rather than full detail — legibility over fidelity, matching the star map's own approach to fog/landmarks.
- **Closing the overview returns to the existing 1:1 editor view** — the current drag-to-move, drag-to-trash, `#editorBar` toolchain, completely unchanged. This is where **fine adjustments** happen: nudging a planet's exact position, sizing (MM-15), and everything Test Play already does. Nothing about today's 1:1 editing model changes; the overview is purely an additional coarse-placement layer *in front of* it.
- On a **small/golf-scale map (the current default)**, the whole canvas already fits one screen at 1:1 — the Overview button still works but has nothing extra to offer, so it can just be hidden/disabled below a size threshold rather than adding a confusing no-op control. (Exact threshold — see Questions below.)

**What this deliberately doesn't do:** no live pan/zoom drag inside a single continuous canvas (that's the parked MAP-3 idea, and it doesn't fit this design — the whole point of the overview is "see the whole map without panning"). No new body types or editor tools. No change to Test Play, save/load, or the sharing/encoding format — `encodeMap()`/`decodeMap()` already store absolute world coordinates, so overview-placed and 1:1-placed bodies are indistinguishable on disk.

### MM-6 — **P1** Map size chooser — ✅ shipped 2026-07-19 (`1f2e3fc`)
A choice (in the editor's start flow, e.g. when hitting "🔨 Map Maker" from the mode menu) between at least a **small/golf-scale** canvas (current 200×200, fits one screen, matches Endless/Golf's feel) and a **large/Explore-scale** canvas (bigger than one screen, needs the overview to place bodies across it). Stored on the map data itself (`mapData.size` or equivalent) so a saved/shared map remembers its scale on load and in `encodeMap()`/`decodeMap()`.
- *Done when:* a new map can be started at either size; the 1:1 editor view and Test Play both work correctly at both sizes (Test Play's camera follows the comet at large scale rather than trying to fit the whole canvas); size round-trips through save, URL share, and import; existing saved maps without a stored size default to the current small/golf-scale behavior (no silent breakage of pre-sprint maps); unit tests cover both sizes' encode/decode round-trip; `node --test` + smoke green.
- **Shipped as spec'd**, resolving the "Map size tiers" question below with option (a) — two fixed sizes: small (200×200, unchanged) and large (600×600, a new `MAP_SIZES` constant). Stored as `world.mapSizeKey` (module state, reset to small on every golf/endless run start) and `mapData.size` on the map itself. `encodeMap`/`decodeMap` only tag 'large' explicitly, so every pre-sprint share link decodes identically to before. The editor's default tee/hole placement, Add Planet/Pulsar centering, the drag-off-canvas delete threshold, and both `stepFlight`/`stepOrbit`'s "lost in space" OOB checks all now read the active map's bounds instead of the hardcoded 200×200 — the last of those was the one real correctness risk (a large map would have falsely triggered "lost in space" around x/y=200 without it). Camera-follow already tracked the comet unconditionally in both editor and custom-map modes, so it needed no change to work at the larger scale. 8 new unit tests + a headless in-browser flight simulation (confirmed OOB now triggers at ~600 on a large map, ~200 on small, matching pre-sprint behavior exactly). Full detail: [Dev Log](../../../archive/dev-logs/black-hole-in-one.md).

### MM-16 — **P1** Editor minimap / overview mode — ✅ shipped 2026-07-19 (`7fd43c1`)
Per the design above. Reuses `renderStarMap()`'s rendering approach (new function, not a literal call — the data source is `world.bodies`/`world.teeRock`/`world.blackHole`, not `explore.discoveredChunks`) for a full-canvas overview with coarse drag-placement, opened/closed via a toolbar button, gated on map size per MM-6 (hidden or disabled on small/golf-scale maps where it has nothing to add).
- *Done when:* on a large/Explore-scale map, the Overview button opens a full-canvas view showing every body as a marker; dragging a body in overview repositions it (verified against the underlying world coordinates, not just visually); closing overview returns to the unchanged 1:1 editor with the new position intact; Add Planet/Add Pulsar work from overview; Test Play, save, and share all work correctly on a map built partly or entirely via overview; on a small/golf-scale map the control is hidden or disabled with no dead click; unit tests cover overview-placement coordinate math; `node --test` + smoke green; verified in-browser building a body across a large canvas via overview, closing it, and confirming the 1:1 view shows the same position.
- **Shipped as spec'd**, hidden (not disabled) below the size threshold, matching MM-6's own tier boundary exactly — 'small' hides it, 'large' shows it, no in-between tier to worry about. The one implementation choice not spelled out above: rather than write new drag-state logic for the overview canvas, the overview's screen-px-to-world-coordinate conversion (`overviewTransform`/`overviewToWorld`/`worldToOverview`, new pure helpers in `constants.js`) feeds straight into `editor.js`'s existing `pointerDown`/`pointerMove`/`pointerUp` unchanged — so overview dragging, the out-of-bounds delete threshold, and Add Planet/Pulsar centering are all literally the same code the 1:1 view already ran, just fed different screen coordinates. Full detail: [Dev Log](../../../archive/dev-logs/black-hole-in-one.md).

### MM-11 — **P1** Play maps directly from My Maps — ✅ shipped 2026-07-19 (`9c34a89`)
Today "▶ Load" in the My Maps drawer always drops you into `edit` phase. Add a direct-play path — either a second "▶ Play" action next to Load, or make Load itself jump straight to Test Play's `rest` phase (build's call which reads better against the existing drawer UI) — so a builder (or someone who imported a shared map into My Maps) can play a saved map without passing through the editor first.
- *Done when:* a saved map can be played end-to-end (aim, flick, sink/score) without an intermediate edit-mode screen; exiting that play session returns cleanly to the drawer or menu (not stuck in editor `edit` phase); existing "Load into editor" behavior is still reachable if the two actions are kept separate; verified in-browser for at least one saved map.
- **Shipped as spec'd, build's call = keep the two actions separate.** A new ▶ Play button hands the map straight to `startCustomMap()` in `gameplay.js` — the exact hand-off a shared `?map=` link already uses, so no new gameplay code was needed, only the drawer's own wiring. Landed in custom mode's `rest` phase, ready to aim and flick. The old load-into-editor action stays reachable, relabeled ✎ Edit (the ▶ Load label would have read ambiguously next to a real Play button); the rename button was relabeled ✏️ Rename for the same reason. Exiting via the existing customBar's ☰ Menu button already worked correctly for this state (it's the same exit the pre-existing shared-map arrival flow uses) — no exit-side code needed. Full detail: [Dev Log](../../../archive/dev-logs/black-hole-in-one.md).

### MM-13 — **P1** Custom Map HUD clarity — ✅ shipped 2026-07-19 (`58529ee`)
Clearer labels for mode/exit while in a custom/shared map — a player should always be able to tell they're in a custom map (not standard Endless/Explore) and see an obvious way out. Builds on STAB-4/5's existing shared-map arrival card and `#customBar`.
- *Done when:* a HUD label or badge is visible during custom-map play identifying it as a custom map; an exit control is present and returns to the main menu; verified in-browser both for a locally-loaded custom map and a `?map=` shared-link arrival.
- **Shipped as spec'd, plus a same-day scope fold-in.** A "🗺️ Custom Map" badge now shows in the top HUD bar whenever `S.mode === 'custom'` — the actual gap, since an exit control already existed (customBar's "☰ Menu" already returned cleanly to the main menu; no change needed there). **Folded in Yev's same-day inbox note** ("maps should be a top level option when clicking on menu so you can play your saved maps"): added "📂 My Maps" as its own top-level section in the main menu, wired to the existing My Maps drawer (MM-2/MM-11), between Play and Make & Explore. **Judgment call, not in the written spec:** exposing that drawer outside the editor surfaced a real bug in the "✎ Edit" action — it silently assumed it was always invoked from an already-live editor session (never set `S.mode`/`S.phase`, never toggled bar visibility). Fixed by making it fully self-contained; also hid "Save/Share Current Map" in the drawer when there's no map actually open (i.e. opened from the main menu rather than mid-edit), so they're not dead taps. Full trail: [Dev Log](../../../archive/dev-logs/black-hole-in-one.md).

### MM-18 — **P1** Object glossary — ✅ shipped 2026-07-19 (`ec77ac6`)
A glossary screen listing every object/mechanic a player or map-builder can encounter, with a one-line plain-language description of how it behaves. Consumes the parked "Object index / bestiary" backlog line and the raw-inbox "glossary of types of objects" note.
- **Scope of entries** (from the actual object/type tags in the codebase — `constants.js`/`explore.js`/`gameplay.js`): tee, black hole (the golf cup / capture spiral), planet (gravity, landable surface), pulsar (repulsor — pushes away), refuel station planet, stardust pickup + stardust ring, fuel pickup, mine, trap, asteroid, decorative moon/ring (cosmetic, no gravity — worth calling out precisely *because* it looks like it should have gravity), plus the core mechanics that aren't "objects" but confuse newcomers the same way — orbit capture, wormhole/warp black holes, Town.
- **Placement:** a new "📖 Glossary" tab alongside Play/Settings/Inventory in the shared ☰ Menu (`#howto`, per HUD-2's tabbed structure) — reachable from normal play, Explore, *and* Map Maker, not gated to the editor. Default choice; flag if Yev wants it Map-Maker-only instead.
- *Done when:* every object type listed above has an entry with a short description; the tab is reachable from the ☰ Menu in all modes including Map Maker; content stays accurate to current behavior (e.g. reflects the current tap-to-land/orbit model, not the old auto-capture one); verified in-browser that the tab opens and content renders in both a golf mode and Map Maker.
- **Shipped beyond the written spec, per Yev's own elaboration when picked up** (*"more than a list of objects... a section for the actions and mechanics... think of it like an achievements system that lets the player know what part of the game they've experienced"*): three sections — 🪐 Objects (the 12 above), ⚙️ Mechanics (flick & gravity aim, landing, orbit capture, refueling, wormhole warp, Town), and 🎛️ Modifiers (reuses the existing Inventory `ITEMS` registry, no duplicated data) — plus a persisted `S.glossarySeen` "✅ Seen"/"❔ Not yet" flag per entry, flipped the first time it's genuinely earned in real play (hole/chunk generation, landing, orbit capture, hole completion, a fuel pickup, a warp, Town Shop's first open, an Inventory item's first toggle-on). Explicitly never marked from Map Maker placement or the decorative boot-background hole/chunk main.js generates behind the start menu — both `genHole()`/`explore.startRun()`/`explore.updateActiveChunks()` gained a `silent` param for that one call site. Resolves the "Glossary scope/placement" question below with option (a). Full trail: [Dev Log](../../../archive/dev-logs/black-hole-in-one.md).

### MM-15 — **P2** Planet size options — ✅ shipped 2026-07-19
Size controls in the map builder (beyond the current random `rand(9,14)` on Add Planet), plus a generally smaller default planet size for tighter, more solvable holes.
- *Done when:* a builder can set or adjust a planet's radius in the editor (1:1 view, per the design above — sizing is a fine-adjustment operation, not an overview one); the default Add Planet size is reduced from the current range; existing saved/shared maps with larger planets still load and render correctly; verified in-browser.
- **Shipped beyond the written spec, per Yev's own elaboration when picked up** (*"i want all of the current object types available and for the ui and ux to be easy to use and navigate"*). Planet size: tap-to-select in the 1:1 view opens a property panel — ➖/➕ radius stepper (new `PLANET_R_MIN`=4/`PLANET_R_MAX`=22/`PLANET_R_STEP`=1.5 constants) and an ⛽ Refuel Station toggle; `addPlanet()`'s default dropped from `rand(9,14)` to `rand(6,10)`. Object types: the Add-object row grew from 2 to 6 — 🌀 Trap and 💥 Mine (reuse `world.bodies` + the existing generic hit-test/drag/delete, zero new plumbing) plus 🟢 Fuel and ✨ Stardust pickups (new `world.pickups` editor support — hit-test, drag, delete, Test Play backup/restore, and full save/share/import including two new `encodeMap`/`decodeMap` tags). The refuel toggle's flag is a 7th, appended field on the planet's encode tuple, so every pre-MM-15 share link still decodes byte-identically. MM-16's overview canvas got the same 6 tools plus matching-color glyphs for all 4 new types. **Two real bugs fixed to make this safe, not cosmetic:** `triggerHazardDeath()` had no recovery path outside Endless mode (traps/mines never spawned there before, so it was never exercised) — a Map-Maker-placed mine hit in golf/editor Test Play/a custom map would have permanently stuck the comet; fixed by respawning at last rest outside Endless, same recovery the out-of-bounds case already uses. Pickup collection in `stepFlight()` was hard-gated to Endless — widened to include `custom`/`editor` so placed pickups actually do something. **Deliberately not built, flagged not silently dropped:** asteroids (found, in passing, that `main.js`'s asteroid-stepping gate checks a dead `S.mode === 'survival'` value — asteroids don't move in *any* current live mode, a pre-existing bug logged separately in Improvements) and decorative moon/ring/stardust-ring authoring (multi-parameter procedural dressing, not a simple placement toggle — logged as a follow-up). 19 new unit tests, full suite 403/403 green, `npm run smoke` clean, verified live in-browser (all 6 object types placed/rendered correctly in both 1:1 and overview views, resize/refuel panel confirmed interactively, hazard-death fix confirmed via Test Play, and a live encode→decode round trip in the browser console confirmed all new fields survive). Full trail: [Dev Log](../../../archive/dev-logs/black-hole-in-one.md).
