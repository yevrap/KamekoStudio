### Iteration 5 revision — Bomber redesign (supersedes the blocked-detection Breaker) — ✅ shipped 2026-07-21

**Why:** playtesting iteration 5 found the shipped mechanic effectively unreachable. A Breaker can only be trapped if sealing it off doesn't also cut spawn's only route to the core — but spawn must *always* stay reachable (unconditional, so future spawns never get permanently stuck), and in a normal single-corridor maze there's only one route, period. Any wall that would trap a Breaker there gets rejected with the same "🚧 Path must stay open" toast as any other build, same as for a normal enemy. Trapping one only works if the player deliberately builds a redundant loop/fork — a maze shape nobody naturally builds, and the game never teaches. Confirmed via Yev's own playtest ("I see the new units but I can't make a blocking path"). Decision (2026-07-21, chat): replace the blocked-then-attack mechanic entirely with a **fuse-based self-destruct** — doesn't care about maze topology at all, so it works identically in a corridor or a loop.

- [x] **P2** Rework the second enemy type into **Bomber** (renamed from Breaker) — same wall/pathing rules, HP, and speed as the base enemy, but now carries a fuse timer instead of blocked-detection. If it's still alive when the fuse runs out, it detonates: flat AoE damage to **every** tower within a blast radius, then the Bomber is consumed (no leak, no kill-gold — it wasn't killed by the player). If towers kill it before the fuse expires, it just dies normally, no explosion. The fuse gets shorter at higher waves (more urgency late-game, Yev's explicit ask) — separate scaling knob from the existing spawn-chance ramp. **Shipped 2026-07-21 (commit `c4eab4b`, deploy verified via Pages):** `wouldSeal()`'s Breaker exemption reverted (`cellOccupiedActiveEnemies()` back to no-arg, unconditional for all enemies); `findAdjacentTowerToAttack()`, `updateBreakers()`'s blocked-timer/attack-key logic, the dashed attack-line + warning-ring visuals, and `BREAKER_BLOCK_DELAY`/`BREAKER_DPS` all removed. Added `bomberFuseSeconds(wave) = max(4, 9-(wave-6)*0.15)` captured once at spawn as `enemy.fuse`/`fuseMax`; `updateBombers(dt)` counts it down and calls `detonateBomber()` at zero, which collects every tower within `BOMBER_EXPLOSION_RADIUS` (1.5 cells) into a list *before* damaging/destroying any of them (avoids mutating `state.towers` mid-scan), deals `BOMBER_EXPLOSION_DMG` (30 flat) to each, and calls the existing `destroyTower()` for anything at ≤0 hp. Fuse-urgency telegraph: a filling ring whose pulse rate increases as `fuse/fuseMax` shrinks. Detonation gets a 30-particle burst, a new `spawnBlast()`/`drawBlast()` radius-flash (fades over 0.35s), and a distinct two-layer `audio.explosion()` cue (low thump + sharp crack) — `audio.towerBreak()` still plays per tower actually destroyed. `bomberChance` (renamed from `breakerChance`) keeps the exact same formula/wave-6 start. **Verified via a temporary debug hook (removed before commit)** driving `updateBombers`/`detonateBomber`/`damageEnemy` directly against the `arcade` preview-pane dev server: an undefended Bomber near two towers (one pre-damaged to 20/40hp, one at full 40hp) detonated for 30 dmg to both — the 20hp one destroyed, the 40hp one survived at 10hp, no core/enemy damage, one blast-flash spawned; a Bomber killed by tower damage well before its fuse expired died with normal kill-gold and zero blast/explosion; `bomberFuseSeconds` confirmed monotonically shorter at later waves (9.75→9→8.4→6.9→4.05→4 floor across waves 1/6/10/20/39/50); zero console errors across the full test session; howto card confirmed showing the new Bomber bullet. Full `node --test tests/` suite (439/439) green — no existing modules touched, still no dedicated maze-warden test file (still in `drafts/`).

  **Remove entirely** (all tied to the abandoned blocked-detection design):
  - `wouldSeal()`'s Breaker exemption — revert `cellOccupiedActiveEnemies()` to no args, unconditional for all enemies again. This restores the original "every active enemy always has a path" invariant for everyone, Bombers included — topology no longer matters at all for this mechanic.
  - `findAdjacentTowerToAttack()` (nearest-bordering-tower BFS), `updateBreakers()`'s blocked-timer/attack-key logic, the dashed attack-line + filling-warning-ring visuals, the `BREAKER_BLOCK_DELAY`/`BREAKER_DPS` constants.
  - The "🧨 A sealed-in Breaker starts smashing an adjacent tower until a path reopens" howto bullet.

  **Keep/reuse:**
  - Tower `hp`/`maxHp`, the damaged-tower tint + hp bar, `destroyTower()` (called per tower reduced to ≤0 hp by the blast — collect matching towers into a list *before* damaging/destroying any of them, don't mutate `state.towers` mid-scan).
  - The existing wave-mixing ramp — same formula, just renamed `breakerChance` → `bomberChance`: `min(0.15 + (wave-6)*0.03, 0.5)` from wave 6 onward.

  **Add:**

### Iteration 7 — Gold-sink inflation & Bomber-damage bugfix — ✅ shipped 2026-07-21

**Why:** Yev's own many-wave playtest of iteration 6 (2026-07-21, logged as `meh` in [Kameko Playtest Log](../../playtest-log.md), overriding the agent-verified pending `keep`) found the "too easy / maxes out fast" complaint still there: *"I get too much money and nothing to spend it on and the game maxes out everything pretty quick and feels useless and boring in some ways."* **Diagnosis:** iteration 6 deepened the Essence/Upgrades meta-economy and the late-wave curve, but never touched the **in-run gold economy** — a fully-built, fully-maxed maze has a fixed, low-thousands-gold ceiling (`80g`/`115g`/`50g` to max a Spire/Prism/Volt, across a 112-cell board), reached within the first 15–25 waves, while per-wave gold income grows faster than linear (`killReward(n) × waveEnemyCount(n)` + `waveClearBonus(n)`, ~580g/wave by wave 30, ~1,325g/wave by wave 50) and never converts to Essence. Every coin earned past that ceiling is currently wasted — no system spends it. **Promotion to the main arcade was gated on this pass** (Yev's words: "I want the game to feel less flat and simple before promoting it") — **cleared 2026-07-21, Keep verdict, promoted the same day.** Q1=C confirmed the "solved maze, nothing left to think about" half is real too, but **Q3=A explicitly deferred it** — ship the gold fix alone, re-test, decide on a follow-up after. A Bomber bug Yev surfaced in the same chat (towers not visibly taking damage) is bundled in below since it's a bugfix, not a new system — low risk of muddying the gold-fix playtest read.

- [x] **P1 — Escalating tower cost ("inflation") (Q2=A ⭐, the leanest single fix Yev picked)** — every additional tower *placed* this run (any type, one cumulative counter, never decremented by selling) makes the *next* tower's construction cost progressively more, via a new run-scoped counter (e.g. `state.towersBuiltThisRun`) feeding a multiplier into `effectiveCost()` at the moment of initial build only — upgrading an already-placed tower to its next level keeps its existing per-level `TOWER_DEFS` cost untouched, matching iteration 6's "don't retroactively change what's already banked" precedent. First-guess formula, same category as the Bomber's fuse/damage/radius numbers (flag for retune once Yev's fresh playtest lands): `costMultiplier = 1 + 0.05 × towersBuiltThisRun` — roughly 1.5× by the 10th tower built this run, ~2× by the 20th, ~3× by the 40th (board caps at 112 cells).
  - **Correctness gotcha, worth stating explicitly:** the 60%-refund sell price must be computed from the gold actually paid for *that specific tower instance* at build time (store it on the tower object, e.g. `tower.builtCost`), not recomputed from the current, higher multiplier — otherwise selling an early cheap tower late-game refunds more than it cost, an exploit that quietly defeats the entire mechanic.
  - *Done when:* building the same tower type costs visibly more late in a run than early in the same run (displayed cost already reflects it, no new UI needed); selling any tower refunds exactly 60% of what was actually paid for it, never more, regardless of how much the multiplier has since climbed; upgrading an already-placed tower's cost is unaffected by how many other towers have been built since.
  - **Shipped (commit `47c6654`, deploy verified via Pages):** `state.towersBuiltThisRun` added to `freshState()` (resets every `resetGame()`), incremented in `placeTower()` on every successful build, never touched by `sellTower()`. `effectiveCost(baseCost, isInitialBuild)` gained a second parameter — `isInitialBuild` (a new `towerInflationMultiplier() = 1 + 0.05 × towersBuiltThisRun` only applies when true) — wired to `true` at both `placeTower()` and the build-sheet cost display, left as the original 1-arg call (no inflation) at `upgradeTower()` and the upgrade-sheet cost display. The correctness gotcha turned out to already be handled: `tower.spent` (pre-existing, accumulates actual gold paid across build + every upgrade) was already what `sellTower()`'s 60%-refund reads from, not a recomputed cost — so no new `builtCost` field was needed, just confirmed the existing field already does the job. Verified live in the preview-pane dev server through the actual production UI event path (not just the debug hook): build-sheet cost rose 25→26→28→29→30g across the first five placements exactly matching the formula; upgrade cost stayed flat at 20g regardless of towers built; sell refund showed 15g for the 1st tower (spent 25) vs 17g for the 4th (spent 29) — different towers, correct per-tower refunds, no exploit. Full `node --test tests/` suite (439/439) green — no existing modules touched.
